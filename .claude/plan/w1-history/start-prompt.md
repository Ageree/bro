# Юнит W1: «Все чаты» и списки — курсорная пагинация

Ты исполнитель. Сначала прочитай `.claude/plan/PROTOCOL.md` (этой же служебной ветки
`origin/claude/speedup-plan`), `AGENTS.md`, `docs/dev-notes.md`. Ветка юнита —
`claude/speed-history` от свежего `origin/bro-next`. Параллельно идут W2 (страница
одного чата `/chat/[sessionId]`, `app/(authenticated)/chat/[sessionId]/**`,
`app/(authenticated)/chat/_lib/session-history*`, `web/components/ai-elements/**`) и W3
(`/workspace` обзор и `/workspace/admin`): их файлы не трогай.

## Что нашёл координатор (прод, 18.10, аккаунт владельца)

- `/chat/history` отдаёт **1,76 МБ HTML** за раз: 1259 чатов, у каждого строка-ссылка;
  `listChats(scope)` (`db/services/chats.ts`) читает все, страница считает расход по всем
  (`combineChatUsage`). Остальные страницы — 25–90 КБ. JS страницы — 848 КБ (264 КБ сжато).
- TTFB всех страниц с машины сессии ≈ 0,5 с — это сеть прокси (404 отвечает за те же
  0,47 с), то есть время сервера маленькое; мерить надо размер ответа, число строк из
  базы и время запроса, а не TTFB снаружи.

## Что сделать

1. `/chat/history`: первая порция (порядка 30–50 чатов, подбери по замеру) и «Показать
   ещё» по курсору (keyset: `(updated_at, session_id)` или то, по чему список сортирован
   сейчас, — не OFFSET). Сумма расхода и число чатов — одним агрегатным запросом в базе,
   а не суммой по всем строкам в JS. Метка «основного треда» (`mainThreadLabels`) должна
   остаться верной при частичной загрузке. Индекс под сортировку курсора (миграция
   поверх свежего bro-next). Предзагрузка следующей порции у края списка — если она
   дешёвая (IntersectionObserver на клиентском островке), иначе кнопка.
2. Посмотри так же `/workspace/memory` и список расписаний (`/workspace` → раздел
   расписаний: только код чтения списка в `db/services`, страницу обзора не трогай —
   её делает W3): есть ли неограниченные списки, N+1, сортировка без индекса. Чини
   то, что даёт измеримый выигрыш.
3. Замеры: размер HTML и число строк до/после на сгенерированных данных (1000+ чатов в
   PGlite/локальном Postgres), `EXPLAIN ANALYZE` запроса до/после индекса.

## Ограничения

- Не меняй формат хранения чатов и `session_id`. Ссылки `/chat/<id>` остаются прежними.
- Агент и `agent/**` не трогай.
