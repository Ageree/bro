# Переход браузерной части Бро на Cloud.ru

Дата исследования и согласования направления: 27 сентября 2026 года.

Статус: архитектурный план, не описание уже выполненной миграции. Продакшен
не переключён. Возможности библиотек проверены по исходникам, облачные
возможности и цены — по документации поставщиков. 28 сентября 2026 года
прошёл пилот этапа 1 на реальной VM Cloud.ru без прокси — итоги в
[разделе 12](#12-итоги-пилота-этапа-1-28-сентября-2026): главный вывод —
OpenRouter, OpenAI и Anthropic отвечают адресам Cloud.ru 403, поэтому
модельные вызовы из VM напрямую невозможны.

## Решение

Первый обязательный этап — перенести браузерную часть с Browser Use Cloud
на собственные пользовательские VM в Cloud.ru Evolution. Перенос всего
приложения и остальных внешних сервисов не является условием этого этапа.

Согласованная целевая схема:

- Основной Бро работает в общем постоянно доступном серверном приложении,
  обслуживающем изолированные пользовательские сессии. Не разворачиваем
  отдельную копию всего продукта на VM каждого пользователя.
- Персональная VM включается по необходимости для браузера, файлов и
  выполнения программ. Обычный ответ, API-интеграция или напоминание не
  требуют запуска VM.
- Данные пользователя сохраняются между запусками. Профиль браузера остаётся
  на постоянном диске; документы можно подгружать из объектного хранилища.
- Chrome/Chromium, его профиль, браузерный исполнитель и residential-прокси
  контролируются Бро, а не Browser Use Cloud.
- JEV выбирает операции и элементы; выбранная текстовая модель помогает
  формировать ввод. Это допустимый прозрачный исполнитель, а не обязательная
  передача всего поручения независимому разговорному агенту.
- JEV остаётся заменяемым компонентом. Прямое управление основным Бро и
  передача управления человеку должны работать без него.

Главный выигрыш — владение средой, наблюдаемость и возможность доработки.
Ускорение и снижение полной себестоимости необходимо доказать собственными
замерами; они не следуют автоматически из self-hosting.

## 1. Где живут Бро и пользовательская среда

```text
Веб-чат / Telegram / другие каналы
                 │
                 ▼
Общее серверное приложение Бро
  • авторизация и пользовательские сессии
  • основной агент eve и обращения к моделям
  • память, разрешения, лимиты и учёт задач
  • расписания и фоновые задания
  • управление жизненным циклом пользовательских VM
                 │
       ┌─────────┼───────────────┐
       ▼         ▼               ▼
   Postgres   Объектное       Авторизованный шлюз
              хранилище      к пользовательским VM
                                 │
                                 ▼
                    Персональная VM пользователя
                      • Chrome / Chromium
                      • браузерный исполнитель
                      • постоянный профиль
                      • рабочие копии файлов
                      • изолированное выполнение кода
                                 │
                                 ▼
                        Residential-прокси
                                 │
                                 ▼
                               Сайты
```

Общий сервер знает владельца задачи, допустимые действия, местоположение
файлов и момент пробуждения VM. Он остаётся доступным, даже когда все
пользовательские VM выключены. Планировщик может прочитать календарь через
API без браузера, а для проверки сайта включить нужную среду.

VM — рабочая среда одного пользователя, а не отдельная установка базы,
биллинга, бота и всей инфраструктуры Бро. Между пользователями не разделяются
профили браузера и рабочие файлы. В текущей модели персональных workspace
привязка идёт к существующему авторизованному владельцу, не к отдельному
чату. При появлении общих workspace доступ к личным аккаунтам нельзя
автоматически расширять на всех участников.

Во время первой миграции общий runtime остаётся на Vercel и обращается к
своим browser workers в Cloud.ru. Позже его можно перенести на общую
постоянную VM с контейнерами приложения в Cloud.ru. Kubernetes на старте
не нужен; разделение веб-приложения и агентских воркеров, репликация и
отказоустойчивость вводятся по измеренной нагрузке.

Размещение Бро на VM не означает размещение весов языковой модели на той же
машине. Модель может оставаться API. GPU на каждой пользовательской VM не
нужен; возможный собственный inference лучше выделять в общий сервис.

## 2. Сохранение данных и работа с файлами

| Данные                                          | Предлагаемое место                                                     | Причина                                                   |
| ----------------------------------------------- | ---------------------------------------------------------------------- | --------------------------------------------------------- |
| История, память, настройки, разрешения и задачи | Общая база и постоянное хранилище состояния eve                        | Нужны при выключенной VM.                                 |
| Пользовательские документы и готовые результаты | Объектное хранилище, каталог и версии в базе                           | Просмотр списка и скачивание не требуют VM.               |
| Файлы активной задачи                           | Рабочая копия на диске VM                                              | Программы работают с обычной локальной файловой системой. |
| Профиль Chrome                                  | Постоянный диск либо выделенная область постоянного диска пользователя | Нужны корректные блокировки и запись профильных баз.      |
| ОС и установленный софт                         | Подготовленный версионированный образ                                  | Среду можно пересоздать без потери данных.                |
| Пароли и служебные ключи                        | Отдельное защищённое хранилище                                         | Произвольный код не должен читать их как обычные файлы.   |

Типовой цикл обработки документа:

1. Бро находит нужную версию файла по каталогу, не запуская VM ради списка.
2. После пробуждения среды загружает только нужные файлы в рабочую папку.
3. Обрабатывает локальные копии и создаёт результат.
4. Сохраняет результат в объектное хранилище и фиксирует версию в базе.
5. Сообщает об успешном сохранении только после подтверждения постоянной
   записи, а не после создания временного файла внутри VM.

Сохранение должно учитывать повтор исполнения задачи и конкурирующие
изменения: нельзя молча перезаписать более новую пользовательскую версию.
Перед выключением выполняется проверка незавершённых сохранений; после сбоя
восстанавливается журнал незавершённой работы. Обычные файлы и профиль
браузера не должны попадать в общедоступные объекты или логи.

Не монтировать объектное хранилище как файловую систему для живого профиля
Chrome без отдельного доказательства корректности. В профиле есть базы и
файлы, чувствительные к блокировкам и семантике записи. Для первой версии
использовать постоянный диск. Архивирование корректно закрытого профиля в
объектное хранилище можно исследовать позже для редко используемых сред.

«Сохраняем между запусками» означает постоянные данные и состояние задачи,
но не замороженную оперативную память. После остановки VM не гарантируется
восстановление произвольного JavaScript-контекста, незаписанной формы или
истёкшей серверной сессии сайта. Бро должен проверить страницу и продолжить
с сохранённой контрольной точки, при необходимости запросив повторный вход.

## 3. JEV и текстовая модель

Нужно различать `jev-ultrafast`, открытый Python-код исполнителя, и Jev,
модель структурированных решений TypeSafe. Проверенный код:
[`1231850`](https://github.com/browser-use/jev-ultrafast/tree/1231850a0bf1a0c0341fe408ef1668dbbfdfac46).

Штатный цикл:

```text
Наблюдение страницы → JEV выбирает операцию и элемент
                                  │
                         если TYPE_TEXT
                                  ▼
                      текстовая модель пишет строку
                                  │
                                  ▼
                     код проверяет и выполняет действие
                                  │
                                  ▼
                          новое наблюдение
```

Это не новый браузер и не ускоренный Playwright. JEV сокращает стоимость
выбора действий за счёт ограниченного пространства операций и targets;
исполнитель оптимизирует наблюдение и взаимодействие с браузером.

### Граница self-hosting

Chrome, Browser Harness и Python runtime можно разместить на своей VM,
без Browser Use Cloud. Но в проверенном
[`model.py`](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/jev_ultrafast/model.py)
решения запрашиваются у `https://api.typesafe.ai/v1/systemone`.

В публичных официальных материалах не найден подтверждённый способ
самостоятельно развернуть именно TypeSafe Jev: опубликованные веса,
inference server или инструкция on-prem. До письменного подтверждения
поставщика считать его внешним API. Сторонние проекты с похожими названиями
не являются официальной моделью и требуют отдельной оценки качества.

### Текстовый helper и данные

`TEXT_MODEL_BASE_URL`, `TEXT_MODEL` и `TEXT_MODEL_API_KEY` позволяют выбрать
свой OpenAI-compatible endpoint. Необходимо проверить совместимость
`response_format` и параметров reasoning. Можно использовать ту же модель,
что у Бро, но это будет отдельный вызов с коротким контекстом, а не текущий
разговор основного агента.

Если текст требует полной истории Бро, исполнитель должен вернуть запрос
на ввод основному агенту, затем принять конкретное значение и заново
проверить актуальность поля. Это адаптация handoff, не просто изменение
переменной модели. Пароли, OTP и известные значения не генерируются:
доверенный код подставляет их из разрешённого источника на проверенном сайте.

TypeSafe получает URL, заголовок, видимый текст, элементы с их значениями
и недавние действия. Text helper получает цель, поле, часть текста страницы
и историю действий. Даже локальный helper не локализует весь inference:
введённый текст может оказаться в следующем наблюдении для TypeSafe.

Ключи общих модельных провайдеров не должны становиться доступными
пользовательскому коду в VM. Вызовы идут через доверенный ограниченный шлюз
или иной проверенный механизм выдачи узких временных полномочий.

MIT относится к коду `jev-ultrafast`, не к сервису TypeSafe и его весам.
Перед production проверить применимый договор, доступность сервиса,
обработку данных и ограничения. В опубликованном [MCA](https://typesafe.ai/legal/mca)
есть отдельные ограничения на публикацию benchmarks и обучение имитирующих
моделей на результатах. Внешний selector — осознанный компромисс на пути
миграции, а не заявление о полностью российской обработке данных.

### Ограничения и честная оценка ускорения

На дату исследования MVP не поддерживает полноценный обход iframe и shadow
DOM, canvas, uploads, новые popup tabs, вложенный скролл и произвольные
клавиатурные виджеты. Это существенно для входов, платежей и загрузки
документов. Успешный выбор `DONE` не доказывает выполнение задачи.

В [отчёте авторов](https://github.com/browser-use/jev-ultrafast/blob/1231850a0bf1a0c0341fe408ef1668dbbfdfac46/docs/performance.md)
Google Flights выполнен за 7,073 секунды, но запуск браузера, первоначальная
навигация и независимая финальная проверка не входят в время. Сравнение
медиан 9,450 → 7,092 секунды — по три запуска двух версий собственного
runtime на одной задаче, не сравнение с Бро или Browser Use Cloud. Стоимость
двух text-helper calls в отчёте не является полной стоимостью задачи.

Полезные идеи для собственного исполнителя: компактный атомарный snapshot,
привязанные к наблюдению ссылки на элементы, проверка свежести и перекрытия
элемента, меньше protocol calls, ожидание полезного изменения вместо
фиксированных длинных пауз. Они применимы и без JEV, но не гарантируют его
скорость при другой модели и сетевом маршруте из РФ.

## 4. Браузерный исполнитель и два режима управления

Open-source Browser Use не требует Browser Use Cloud для локального браузера
или собственного CDP. В версии 0.13.10, commit
[`4cbe921`](https://github.com/browser-use/browser-use/tree/4cbe921673b48a488f5415d9159249afd12a625b),
подтверждены `BrowserSession.get_browser_state_summary()` и `Tools.act()`:
можно получать состояние и выполнять конкретные действия без `Agent.run()`.
Обработка DOM сама по себе не является вызовом LLM.

Внешний контракт Бро должен быть небольшим и собственным: открыть страницу,
получить состояние, нажать элемент, ввести текст, выбрать значение,
загрузить/скачать файл, остановить работу и передать управление человеку.
Внутри можно использовать pinned Browser Use, Browser Harness или Playwright.
Не делать внутренний формат молодой библиотеки контрактом всей системы.

Планируются два режима на одном браузере:

- JEV выполняет ограниченные короткие участки с заданной целью, бюджетом
  времени и действий. Каждый шаг и причина остановки доступны Бро.
- Основной Бро выбирает конкретные действия при сложной странице,
  неподдерживаемых элементах или необходимости полного контекста.

Резервный режим должен обходить ограничения считывателя JEV, а не только
спрашивать другую модель о той же неполной DOM-картине. Для одной вкладки
всегда один управляющий исполнитель; переключение JEV, Бро и человека
производится явно. DOM ref действителен только для соответствующего
наблюдения, страницы и версии состояния.

Не заменять Cloud `POST /runs` локальным `Agent.run()` как конечную цель:
это переносит хостинг, но сохраняет отдельного автономного агента. Не
выдавать unrestricted Python, JavaScript или raw CDP за безопасный API
нажатий. LLM-backed extraction и agent fallback некоторых библиотечных
tools должны быть включены только осознанно.

## 5. Жизненный цикл пользовательской VM

Для первой версии создавать VM при первом реальном использовании, затем
включать и останавливать её с сохранением дисков. Не создавать VM каждому
зарегистрировавшемуся заранее и не вводить тёплый пул без замеров.

1. Общий сервер проверяет владельца задачи и получает lease на среду.
2. Включает существующую VM или создаёт её из подготовленного образа.
3. Проверяет готовность исполнителя, профиль, прокси и необходимые файлы.
4. Выполняет задачу, сохраняя прогресс и результаты вне эфемерного процесса.
5. После завершения сохраняет файлы и корректно закрывает браузер.
6. По истечении ограниченного периода простоя выключает VM.

Lease и поколение владельца должны предотвращать управление старым worker
после передачи среды новому. Нужны отмена задачи, heartbeat и восстановление
после исчезновения процесса. Две команды одного пользователя не должны
породить конфликтующие процессы с одним профилем Chrome.

Ожидание OTP, ручного входа и незавершённого действия — отдельные состояния.
На ограниченное время браузер остаётся живым; при истечении ожидания задача
паркуется с явным объяснением возможного повторного входа. Нельзя выключать
VM посреди отправки и считать потерю ответа доказательством неуспеха.

Период простоя подбирать по нагрузке: мгновенное выключение после каждого
сообщения ухудшит UX следующего шага. Программы и браузерные зависимости
должны быть в образе, не устанавливаться заново при каждом включении.

Позже можно исследовать пересоздаваемые VM с пользовательским диском,
холодное архивирование профилей и небольшой тёплый пул. Нельзя передавать
следующему пользователю неочищенную среду. Остановка VM сама по себе не
является очисткой или гарантией освобождения облачной квоты.

## 6. Возможности и ограничения Cloud.ru Evolution

Исследование относится к Evolution, не к Advanced. [Реестр API](https://cloud.ru/docs/console_api/ug/topics/overview__reestr_api?source-platform=Evolution)
ведёт к [Compute API](https://cloud.ru/docs/virtual-machines/ug/topics/api-ref-v3).
Для новой интеграции актуальная спецификация рекомендует
`POST /api/v1.1/vms`; `/api/v1/vms` — прежний вариант создания.
Питание управляется через `POST /api/v1/vms/{vm_id}/set-power`, удаление —
через `DELETE /api/v1/vms/{vm_id}`. Есть cloud-init, операции с дисками,
attach/detach, резервные копии и сервисные задания.

API обслуживается сервисным аккаунтом с необходимыми ролями. Управляющий
ключ остаётся у общего сервиса, не у пользовательских VM. Сервисные роли
проекта не заменяют проверку принадлежности конкретного ресурса человеку.
См. [аутентификацию](https://cloud.ru/docs/console_api/ug/topics/guides__auth_api)
и [роли VM](https://cloud.ru/docs/virtual-machines/ug/topics/security).

Практические ограничения:

- [Создание](https://cloud.ru/docs/virtual-machines/ug/topics/faq__vm-creation-time)
  первой VM из нового образа обычно занимает не более пары минут; следующие
  создаются быстрее. Это не SLA, не p95 и не время включения остановленной
  машины. Нужен замер полного пути до готового браузера.
- [Типовые квоты](https://cloud.ru/docs/virtual-machines/ug/topics/overview__limitations?source-platform=Evolution)
  включают 10 VM, 8 vCPU и 512 ГБ дисков на организацию. Для пилота и роста
  согласовать реальные квоты. Освобождение квот при STOP не подтверждено:
  прекращение оплаты вычислений не означает освобождения квоты.
- [Диск](https://cloud.ru/docs/disks/ug/topics/concepts__disks) можно
  переподключить к другой VM в той же зоне доступности, но не использовать
  одновременно на нескольких VM. Это ограничивает размещение и восстановление.
- VPC, security groups и общий sNAT позволяют не выдавать публичный IP
  каждой VM. sNAT не является residential-прокси: маршрут браузера через
  купленный прокси настраивается отдельно.
- Точная комбинация оплаты sNAT, его IP и исходящего трафика требует
  подтверждения. FAQ на дату исследования называет трафик временно
  бесплатным, хотя в тарифе есть отдельная строка.

По документации Evolution подходит для пилота. Готовность конкретного
проекта по квотам, latency, доступности флейворов и сетевой политике этим не
доказана. Container Apps и Kubernetes не являются проверенной заменой
персональной VM с постоянным интерактивным браузером; их не вводить только
ради слова scale-to-zero.

пользовательские диски. 2 vCPU / 4 ГБ — исходная конфигурация для проверки,
а не доказанная достаточность для любых сайтов и обработки документов.

В сумму не входят модель Бро, JEV, text helper, прокси и его трафик,
объектное хранилище, backup, общая инфраструктура и эксплуатация. Время
запуска, ожидания человека и простоя до выключения входит в активность VM.

```text
Себестоимость пользователя =
  ставка VM × часы работы
  + постоянные диски
  + объектное хранилище и его операции
  + резервные копии
  + модели и JEV
  + прокси и сеть
  + доля общей инфраструктуры и эксплуатации
```

При умеренной активности постоянный SSD может стоить больше вычислений.
Поэтому большие коллекции документов подгружаются по запросу. Небольшой
постоянный диск для профиля на первом этапе оправдан простотой восстановления.
Тарифы с гарантированной долей CPU 10%/30% исследовать отдельно: ухудшение
latency может удлинить задачу и уменьшить экономию.

## 8. Безопасность и подтверждение действий

- Изолировать пользовательский код от профиля браузера, raw CDP и ключей.
  Доступ скрипта к cookies или DevTools обходит разрешения browser tools.
  Файловая песочница и доверенный исполнитель требуют разных полномочий.
- VM и её ресурсы выбираются по авторизованному владельцу. Не принимать
  произвольный VM ID от модели как доказательство права доступа.
- Закрыть CDP от интернета, ограничить обращения к внутренним сервисам и
  cloud metadata. Domain allowlist библиотеки не заменяет сетевую изоляцию.
- Секреты подставлять только на проверенных доменах. Снимки, URL, DOM,
  traces и профили считать чувствительными данными; отключить ненужную
  телеметрию и проверить фактический сетевой выход.
- Подтверждения и лимиты проверяет код. JEV или другая модель не создают
  новые разрешения собственным решением. Не считать confidence авторизацией.
- Универсальный click не доказывает семантику любой кнопки. Для критичных
  операций нужны проверяемые сценарии и контроль итогового действия; при
  неопределённости передавать управление человеку, а не обещать абсолютную
  защиту промптом.
- После таймаута отправки не повторять действие вслепую. Журнал команд,
  дедупликация и проверки результата уменьшают риск дублей, но не создают
  exactly-once гарантию у произвольного стороннего сайта. Неясный исход
  требует сверки, а не автоматического повторного заказа.
- Содержимое сайтов и файлов — недоверенные данные. Prompt injection не
  исчезает при переходе от двух моделей к одной.

Residential-прокси не гарантируют отсутствие CAPTCHA, блокировок и повторного
2FA. По возможности сохранять стабильную сессию прокси для аккаунта,
не ротировать IP после каждого действия. Настройка прокси Chrome не означает
маршрутизацию всей VM через него. Предусмотреть защищённый ручной вход и
возврат управления агенту без одновременных действий человека и автоматики.

## 9. Российское размещение данных

Свой браузер в Cloud.ru не означает, что весь Бро обрабатывает данные в РФ.
Текущие внешние зависимости описаны в
[`agent/lib/privacy/facts.ts`](../agent/lib/privacy/facts.ts): Vercel,
Neon, Vercel Blob, OpenRouter, Composio и опциональный Supermemory. При
использовании JEV TypeSafe становится отдельным обработчиком содержимого
страниц. Перенос базы не переносит автоматически историю Vercel Workflow.

Миграция идёт по слоям: сначала браузер и рабочая среда; затем общий runtime,
база, история и файлы; отдельно модельные провайдеры и интеграции. Для
чувствительных сценариев может потребоваться запрет передачи страницы
внешнему selector. Маскировка полей не является гарантированным
обезличиванием всего содержимого.

[Материалы Cloud.ru о соответствии](https://cloud.ru/docs/evolution/overview/topics/security__compliance)
не заменяют проверку применимости 152-ФЗ к приложению. Нужны собственные
решения по доступу, срокам хранения, удалению, обработчикам и внешним
передачам, особенно для государственных, медицинских и платёжных данных.
Этот документ не является юридическим заключением.

## 10. План реализации и критерии готовности

Этапы ниже пока не выполнены; по этапу 1 прошёл пилот без прокси, файлов и
ручного управления (раздел 12). Минимальная цель миграции — этапы 1–5:
браузерная работа в Cloud.ru без зависимости от Browser Use Cloud для
переведённых пользователей. Перенос общего приложения — отдельный этап 6.

### Этап 1. Проверить одну персональную среду

Подготовить образ, поднять VM, настроить свой браузер и прокси, постоянный
профиль, файлы и ручное управление. Проверить start/stop, перезапуск
процесса, повторное подключение, upload/download и восстановление данных.

Готово, когда после выключения и включения файлы доступны, профиль
корректен, состояние задачи проверяется перед продолжением, а чужая среда
недоступна. Отдельно записать latency до готового браузера, расход памяти,
доступность флейвора, minimum disk и реальную тарификацию.

### Этап 2. Подключить собственный браузер к текущему Бро

Оставить основной runtime на Vercel. Добавить типизированные операции,
авторизованный транспорт и события worker. Переиспользовать существующие
разрешения, лимиты, учёт поручений и доставку результата, не переписывая их
одновременно с транспортом браузера.

Текущие точки интеграции:

- [`agent/tools/browser_task.ts`](../agent/tools/browser_task.ts) — поручение,
  согласия и продолжение после ответа человека.
- [`agent/lib/browser-use/client.ts`](../agent/lib/browser-use/client.ts) —
  Cloud V4 и текстовые запуски; это не контракт будущего локального Agent.
- [`agent/schedules/browser-runs.ts`](../agent/schedules/browser-runs.ts) —
  polling, восстановление и доставка. События worker сокращают ожидание,
  но проверка потерянных событий и зависших задач остаётся.
- [`db/services/browser-runs.ts`](../db/services/browser-runs.ts) —
  принадлежность профилей, состояние задач и отчётов.
- [`shared/environment/env.ts`](../shared/environment/env.ts) —
  обязательная граница валидации новых runtime-параметров.

Готово, когда поручение доходит от запроса до проверяемого результата,
останавливается пользователем и не теряется при сбое worker. Уже имеющиеся
свои прокси не являются новой возможностью: миграция нужна ради контроля
над исполнением и состоянием браузера.

### Этап 3. Проверить JEV и прямое управление

На одинаковых сайтах, профилях и прокси сравнить JEV и прямые инструменты
основного Бро. Добавить bounded JEV segments, передачу текста основному
агенту при необходимости и резервный исполнитель для неподдерживаемых
элементов. Убедиться, что переключение не запускает два управляющих цикла.

Готово, когда известны доля успешных задач, полная задержка, стоимость
успешного результата и причины передачи управления. Если JEV не проходит
критерии, это не блокирует самостоятельную браузерную инфраструктуру.

### Этап 4. Автоматизировать lifecycle и сохранение

Реализовать создание по первому использованию, включение, idle-stop,
lease на профиль, очередь конфликтующих задач, подгрузку файлов,
подтверждённое сохранение результатов, квоты и пользовательское удаление.
Проверить восстановление из backup, а не только его создание.

Готово, когда два запроса одного пользователя не конфликтуют, разные
пользователи не видят данные друг друга, а сбой/остановка не теряет
подтверждённо сохранённые результаты. Удаление должно учитывать диски,
объекты и политику истечения резервных копий, не только строку в базе.

### Этап 5. Перевести пилотных пользователей и убрать Cloud-зависимость

Включать новый backend для ограниченной группы, затем расширять по
результатам. Заранее определить, какие старые задачи завершаются на старом
backend и как пользователь повторно входит на сайты. Не обещать перенос
всех cookies и входов между провайдерами без проверки экспорта/импорта.

Backend фиксируется на время конкретного поручения. При сбое после
возможного внешнего действия нельзя автоматически запускать то же
поручение на другом backend: сначала проверить результат. Откат направляет
новые задачи, а не дублирует уже начатые заказы.

Готово, когда переведённый пользователь выполняет согласованный набор
браузерных задач без вызовов Browser Use Cloud, получает результаты и
может воспользоваться ручным входом. После завершения старых запусков
убираются ненужные Cloud-ключи, профили и интеграционные ветки по отдельному
проверенному плану удаления.

### Этап 6. Перенести общий runtime и остальные данные

Eve поддерживает [self-hosting](https://eve.dev/docs/guides/deployment/self-hosting);
путь проверен также по документации закреплённого пакета 0.62.0. Требуются
постоянное хранилище workflow, расписания и маршруты `/eve/` и
`/.well-known/workflow/`. Проверять `pnpm build:eve`, не только Next.js build.

При нескольких репликах локальная папка workflow не становится общей
надёжной базой автоматически: нужен совместимый backend хранения и
очередей. Миграция активных Vercel Workflow-сессий — отдельная задача,
не следствие переноса Postgres. Не допустить двух одновременно активных
планировщиков при переключении.

Готово, когда перезапуск общего сервера не теряет сообщения, задачи и
подтверждения; расписания не дублируются; определён путь для старых сессий.
Модельные провайдеры и OAuth-интеграции мигрируют отдельными решениями.

## 11. Проверки до production

Набор должен включать поиск и фильтры, OTP, iframe, popup, загрузку документа,
скачивание результата, ручной вход, обновление страницы, stale ref,
таймаут после отправки, рестарт worker и VM, гонку двух запросов,
восстановление backup и удаление данных.

Измерять отдельно холодную и готовую среду: p50/p95 до первого полезного
действия, полное время задачи, успешность по независимой проверке,
число повторов, расход моделей/прокси/VM, частоту ручного вмешательства.
Не выдавать `DONE` или отсутствие исключения за успешное поручение.

Использовать существующие [кейсы Бро](benchmarks/README.md) и разрешённые
тестовые аккаунты. Входы в один государственный или иной чувствительный
аккаунт не запускать параллельно. Платежи и реальные отправки не выполнять
ради benchmark без явного разрешения; проверять условия поставщика перед
публикацией сравнений.

Пока остаются открытыми: реальные quota при STOP, стартовая latency,
minimum disk выбранного image, совместимость прокси, суммарная сеть,
условия TypeSafe и его доступность, качество JEV на российских сайтах,
границы переноса старых профилей и история workflow. Эти вопросы решаются
пилотом и подтверждением провайдера, а не предположением в реализации.

### Выводы для следующих этапов

- Модельные вызовы из пользовательской VM напрямую невозможны: OpenRouter,
  OpenAI и Anthropic режут адреса РФ. Нужен шлюз — общий сервер Бро вне РФ
  (раздел 3 и так требует не держать ключи провайдеров в VM) — или модели,
  доступные из РФ (Cloud.ru Foundation Models, TypeSafe). В этом пилоте
  шлюз не строили: он не был частью задачи, а пересылка трафика через
  облачную сессию оператора запрещена её политикой.
- TypeSafe из Cloud.ru доступен и быстр (≈ 0,3 с на решение), но на наших
  задачах jev без текстовой модели не дошёл до цели ни разу; его качество с
  рабочим helper ещё предстоит измерить.
- Прямое управление (снимок состояния browser-use без `Agent.run()`) работает
  на всех сайтах, которые пускают датацентровый адрес: 0,1–0,5 с на снимок.
- Ozon и Avito не пускают адрес Cloud.ru: для них residential-прокси остаётся
  обязательным, как и предполагал раздел 8.
- Госуслуги открываются с адреса Cloud.ru, но через межстраничную заставку:
  исполнитель должен ждать полезного изменения страницы, а не `load`.
- Жизненный цикл подтверждён: включение до готового браузера ≈ 47 с, профиль
  (cookie и localStorage) переживает остановку при штатном выключении.
