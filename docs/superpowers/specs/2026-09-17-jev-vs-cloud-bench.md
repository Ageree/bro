# Jev против облачных моделей: что установлено и как продолжить

Статус на 2026-09-17: **обе дуги прогнаны** на новом наборе навигационных
задач. Главный результат — не время, а то, что jev-ultrafast **не умеет
логиниться в принципе**: поля `type="password"` вырезаны из её пространства
действий по замыслу. Подробности ниже, в «Результаты».

## Что выяснено про Jev

Jev — флагманская модель [TypeSafe](https://docs.typesafe.ai/introduction),
«System One»: принимает состояние и типизированные вопросы (Choice / Score /
Noul), возвращает структурированные ответы с вероятностями и уверенностью.
Текст она не генерирует.

**В Browser Use Cloud её нет и не будет через BYOK.** Дословно из документации
Browser Use: «BYOK means a supported provider credential, not an arbitrary
self-hosted model endpoint». BYOK меняет только то, на чей счёт идут токены
моделей, которые облако уже хостит, поддерживает ровно Anthropic / OpenAI /
Google, и ключ не передаётся в запросе — он лежит в настройках проекта и
подхватывается по совпадению модели. Строки `jev` в схеме V4 нет.

**Но браузер она водит** — через отдельный проект
[browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast),
официальный для Browser Use × TypeSafe. Архитектура:

```
страница → таблица элементов → один запрос к Jev → операция + цель
                                                       ↓
                                   TYPE_TEXT → маленькая LLM пишет текст
```

Jev выбирает операцию (`CLICK`, `TYPE_TEXT`, `SELECT`, `SCROLL_*`, `WAIT`,
`DONE`, `BLOCKED`) и целевой элемент за **один** сетевой раунд; текст пишет
дешёвая `inception/mercury-2.5`, и только когда операция — `TYPE_TEXT`.
Заявленная медианная задержка Jev — **178 мс**, Google Flights целиком за
**7.07 с**.

Их собственные замеры аккуратны: три пары прогонов, медиана −25%, и тут же
оговорка, что `p = 0.25` и трёх пар мало. Ориентир для нас: **25 с у Luna
против ~7 с** на сопоставимой задаче.

Всего $0.097 за 18 ранов. Реальная цена рана — полцента, не центы-десятки.

**Набор упёрся в потолок.** 18 из 18 означает, что различать модели он уже не
может. Плюс `books.toscrape` и `quotes.toscrape` — самые известные учебные

регрессия на извлечение данных набор годен, как измеритель — нет.

## Почему набор нельзя перенести на Jev как есть

`jev_ultrafast.Agent` не возвращает текстовый ответ:

```python
with Agent(url, goals) as agent:
    for state in agent.run():
        state["elapsed_ms"], state["status"], state["page"]["url"]
```

Он доводит браузер до целевого состояния. В их `AGENTS.md` прямо сказано:
«A DONE choice is not proof of success» — результат проверяется независимо.
Наши шесть задач требуют ответа строкой (`COUNT=3 SUM=132.39`). Жанры разные:
облачный агент ходит **и рассказывает**, Jev — только ходит.

**Следствие для замера:** нужен набор задач на навигацию и взаимодействие,
результат которых проверяется **финальным состоянием страницы**, а не
пересказом: открыть нужную карточку, заполнить форму, выбрать в выпадающем
списке, применить фильтры — и сверить итоговый URL. Тогда обе дуги делают одну
работу. Побочная выгода: такие задачи ближе к тому, что Bro реально делает
(логин, оплата, заказ), чем выковыривание цен из таблицы.

Сравнивать «полное время рана» будет нечестно: Cloud поднимает удалённый
браузер через прокси, jev-ultrafast работает с локальным Chrome. Мерить надо
время решений и число запросов, по методике самих Browser Use — от первого
предсказания до принятого `DONE`, подъём браузера и навигация за скобками.

## Состояние окружения

Проверено в контейнере этой сессии:

- `uv sync` в клоне jev-ultrafast проходит; `uv run pytest` — **31/31**.
- Chromium запускается headless с CDP:
  ```bash
  /opt/pw-browsers/chromium-1194/chrome-linux/chrome --headless=new \
    --no-sandbox --disable-gpu --disable-dev-shm-usage \
    --remote-debugging-port=9222 --user-data-dir=/tmp/chrome-profile about:blank &
  ```
- `browser-harness --doctor` после этого видит `chrome running`.
- Демон harness поднимается, `doctor --json` даёт `"healthy": true`. Что
  мешало — ниже.

### Демон не видел Chrome: дело было не в ключе

Гипотеза про `TYPESAFE_API_KEY` **опровергнута** — ключ тут не при чём.

Лог (`~/.config/browser-harness/tmp/bu-default.log`) не существовал, потому
что `doctor` только докладывает и демона не запускает; лог появился после
первого настоящего вызова и содержал одну строку:

```
fatal: chrome-not-running: no supported Chromium-family browser is running
```

При этом сам `doctor` в том же состоянии печатал `"chrome_running": true`.
Противоречие объясняется тем, что две части harness ищут Chrome по-разному:
`admin.py` сканирует процессы, а демон (`daemon.py`) обходит **фиксированный
список стандартных профилей** — на Linux это `~/.config/google-chrome`,
`~/.config/chromium` и ещё несколько. Он ищет в них `DevToolsActivePort` и
`SingletonLock`; `--user-data-dir=/tmp/chrome-profile` для него не существует,
и проверка живости роняет запуск до того, как сработает запасной проб портов
9222/9223.

Лечится тем, что Chrome поднимается в профиль из этого списка:

```bash
/opt/pw-browsers/chromium-1194/chrome-linux/chrome --headless=new --no-sandbox \
  --disable-gpu --disable-dev-shm-usage --remote-debugging-port=9222 \
  --user-data-dir="$HOME/.config/chromium" about:blank &
```

Ещё одна мина рядом: `cdp()` из `browser_harness.helpers` — сырой канал и
сам не лечится. Если Chrome перезапустить после того, как демон к нему
подключился, первый же вызов падает с `no close frame received or sent`.
Поэтому harness замера зовёт `ensure_daemon()` перед работой с `cdp()`.

### Chrome не доверял CA прокси — все HTTPS-страницы были ошибкой

Отдельный блокер, до которого прошлая сессия не дошла. Любой https в этом
Chrome отдавал `chrome-error://chromewebdata/` и «Your connection is not
private»: исходящий трафик переterminируется агентским прокси, а Chrome на
Linux читает не системное хранилище, а NSS (`~/.pki/nssdb`). Хранилище было
**пустым** — `certutil` в образе отсутствовал, так что настройка браузерного
NSS при старте контейнера молча не выполнилась.

```bash
apt-get update && apt-get install -y libnss3-tools
# оба CA из /root/.ccr/agent-proxy-ca.crt
certutil -A -n ccr-agent-proxy-<n> -t "CT,C,C" -i <cert>.pem -d sql:$HOME/.pki/nssdb
```

После импорта и перезапуска Chrome страницы открываются нормально. Проверку
сертификатов при этом никто не отключал.

## Набор навигационных задач

Лежит в `scripts/lib/nav-tasks.ts` — единственный источник правды для обеих
дуг. Дуга Cloud (`scripts/nav-bench.ts`) читает его напрямую, дуга Jev
(`scripts/jev-nav-bench.py`) забирает тот же список через `--dump-tasks`,
так что разойтись в формулировке цели, стартовом URL или критерии успеха они
не могут.

Семь задач, каждая оценивается **только** состоянием страницы, которую агент
оставил, — harness читает её по CDP:

| задача | что нагружает |
|---|---|
| `sauce-login` | форма из двух полей; целевая страница за логином |
| `sauce-cart` | цепочка: войти, выбрать один товар из шести, открыть корзину |
| `sauce-checkout` | самая длинная цепочка: + оформление, три поля, страница обзора заказа |
| `internet-login` | та же форма на другом сайте — отличает навык от совпадения |
| `internet-checkboxes` | прочитать состояние до действия: #1 снят, #2 уже стоит |
| `internet-dropdown` | нативный `<select>` — отдельная операция, не клик |
| `webscraper-product` | витрина: найти названный товар среди шести карточек |

Правила, которым подчиняется каждая задача:

- **Одна формулировка цели, дословно общая для обеих дуг.** Ни селекторов, ни
  списка шагов: `AGENTS.md` в jev-ultrafast запрещает site-specific планы, а
  набор, который их протаскивает, мерил бы промпт, а не политику.
- **Результат нельзя получить угадыванием URL.** Пять задач из семи
  заканчиваются на странице за логином или на чистом состоянии DOM. Cloud
  умеет набрать адрес, а в пространстве действий Jev адресной строки нет
  вообще (только клик, ввод в поле, выбор, скролл, ожидание), так что задача,
  решаемая переходом по ссылке, отдала бы Cloud обход ровно того, что мы
  измеряем. Проверено: прямой переход на `/secure` отбрасывает на `/login`.
- **Эталон посчитан из живого браузера и заморожен в коде.** Свободный режим
  `nav-bench.ts --validate` гоняет каждую проверку через настоящий Chrome и
  требует, чтобы она была `false` на старте и `true` после решения. Модели он
  не зовёт и денег не стоит.
- **Ни одного знаменитого учебного сайта.** `books.toscrape` и
  `quotes.toscrape` — самые растиражированные страницы для скрапинга, часть
  ответов модель может выдать не открывая их.

Отброшено по ходу: `webscraper.io/test-sites/e-commerce/allinone` **тасует
товары в витрине** — три запроса дали три разных набора. Эталон по нему
поехал бы молча, поэтому взято стабильное поддерево `/static`.

### Сброс состояния между попытками — обязателен

saucedemo держит корзину в `localStorage` (`cart-contents`) и логин в куке, и
они переживают закрытие вкладки. Cloud получает свежий браузер на каждый ран,
а дуга Jev живёт в одном долгом профиле: без явного сброса вторая попытка
стартует **уже залогиненной, с корзиной первой**, и всякая проверка корзины
проходит бесплатно. Обе дуги чистят origin перед попыткой.

## Методика времени

Полное время рана не сравнивается и заголовком не является: Cloud поднимает
удалённый браузер через прокси и холодно стартует воркер, jev-ultrafast
работает с Chrome, уже запущенным на этой машине.

Обе дуги мерятся по границе самих Browser Use (`docs/performance.md` в
jev-ultrafast) — **от первого предсказания до принятого DONE**, подъём
браузера за скобками:

- **Cloud**: от первого события `llm.request` до последнего `llm.response` в
  потоке событий рана.
- **Jev**: `state["elapsed_ms"]`, который агент запускает на первом `predict`,
  уже после того как конструктор сходил на страницу и снял первое наблюдение.

Что при этом выбрасывается, видно на пробном ране: `run.created` →
`run.dispatching` → `browser.ready` → `worker.started` → `workspace.ready` →
`core.spawn` заняли **3.2 с из 14.6 с**, и ни секунды из них не про модель.

**Один остаток не убирается.** В `RunCreateRequest` нет поля для уже открытой
страницы — есть только `sessionId`, а он тащит историю разговора предыдущего
рана. Поэтому агент Cloud открывает стартовый URL **внутри своих часов**, а
агент Jev конструируется на странице и начинает считать после этого. Остаток
измеряется и печатается как `navResidualMs`. Смещение работает **против**
Cloud, так что выиграть за Jev оно не может.

Число запросов к модели считается отдельно от времени: одно число — это счёт,
другое — ожидание, и весь замысел Jev именно про форму первого.

### Jev не умеет логиниться — и это по замыслу

Все 12 попыток с формой логина провалились одинаково и воспроизводимо: агент
печатает логин в поле «Username», затем печатает его туда же ещё три раза и
встаёт как `blocked`. Диагностика на двух разных сайтах показывает, почему —
в таблице элементов **нет поля пароля**:

```
{'role': 'textbox', 'value': 'standard_user', 'index': '1', 'label': 'Username', ...}
{'role': 'button',  'value': 'Login',         'index': '2', 'label': 'Login',   ...}
```

Причина в `jev_ultrafast/snapshot.js`, строка 9, применяется при сборе
элементов (строка 57):

```js
const safe = e => !['password','file','hidden'].includes(e.type);
```

Пароли, файловые и скрытые инпуты вырезаны из снимка сознательно — это
решение про безопасность, а не баг. Следствие для замера: **никакая настройка
и никакая другая текстовая модель этого не изменят**, логин для jev-ultrafast
структурно недостижим. Ровно поэтому 9/21 — это три задачи без логина, взятые
трижды.

**Для Bro это важнее любой цифры скорости.** Наши настоящие поручения — это
логин, оплата, заказ. Дуга, которая не может заполнить пароль, закрывает не
край сценария, а его середину.

### Скорость там, где сравнение вообще осмысленно

Три задачи, которые обе дуги решают. Мешать сюда задачи, которые одна дуга не
начинает, нельзя: это записало бы ей один и тот же разрыв дважды — раз
провалом, раз «медлительностью», которой она не тратила.

| дуга | решено | медиана времени решений | медиана запросов |
|---|---|---|---|
| `gpt-5.6-luna` | 9/9 | **14.7 с** | 4 |
| `jev-ultrafast` | 9/9 | **0.6 с** | 2 |

Разница примерно в **24 раза** по времени решений и вдвое по числу запросов.
Форма ровно та, которую обещает архитектура: два запроса против четырёх, и
каждый — короткий.

Заявленную медианную задержку Jev в 178 мс проверили по своему же трафику:
**213.5 мс** на 66 запросах (min 159, max 680). Порядок тот, в этом контейнере
на ~20% выше заявленного.

Число запросов на решённый ран: Cloud медиана 5 (от 3 до **16** на
`sauce-checkout`), Jev — ровно 2 на всех девяти решённых.

### Что вышло с ценой

Модельные траты дуги Cloud за 21 ран — **$0.1338**, около полуцента за ран,
как и в прошлой базе.

Но рядом обнаружилась вторая строка счёта. Завершённый ран **не гасит свой
облачный браузер**, тот висит до четырёхчасового предела; на момент проверки
21 браузер показывал суммарно **$1.68** (по ~$0.08 на живой браузер). После
явной остановки всех фактическая сумма осела на **$0.0083**, то есть $0.08 —
это резерв под предел, а не итог. Практический вывод от этого не меняется:
браузеры надо гасить, и `scripts/nav-bench.ts` теперь гасит каждый сразу
после того, как страница прочитана. В проде то же самое давно делает
`stopBrowserForSession` в `agent/lib/browseruse.ts` — и ровно с этим
комментарием.

### Оговорки

- Дуги стоят на разной инфраструктуре: Cloud поднимает удалённый браузер через
  прокси и холодно стартует воркер, jev-ultrafast работает с локальным Chrome.
  Поэтому полное время рана (26.3 с против 3.8 с медианы) в заголовок не
  берётся и сравнением скорости не является.
- Из часов Cloud вычтено 3.9 с медианы инфраструктуры. Внутри её часов остаётся
  медиана 7.9 с до первого действия в браузере — это **потолок** оценки
  асимметрии стартовой страницы, а не цена навигации: большая часть интервала
  это загрузка браузерного скилла и один-два хода рассуждений, то есть
  настоящая работа агента. Смещение работает против Cloud.
- Три повтора на задачу — мало для статистики. Сами Browser Use в своём
  замере оговариваются про то же (`p = 0.25` на трёх парах).
- Набор всё ещё не различает модели Cloud по решаемости: Luna взяла 21/21, как
  раньше брала 18/18. Различает он теперь время и число запросов (от 3 до 16
  запросов на задачу) — и, как выяснилось, архитектурные дыры.

## Замеченное попутно

`BROWSER_USE_API_KEY` и `OPENROUTER_API_KEY` приходят из хранилища секретов
**с переносами строк внутри значения**. Для Browser Use это ломало каждый
запрос до отправки: `fetch` отвергает такой заголовок сам, и падало это с
ошибкой про заголовки, а не про кривой секрет.

Найдено при первом живом прогоне замера. В проде починено отдельно — PR #114
нормализует ключ в `agent/lib/browseruse.ts` и `convex/lib/browseruse.ts` и
закрывает регрессию в `scripts/browser-policy-check.ts`. `scripts/model-bench.ts`
делает то же самое у себя.

Само значение в хранилище при этом по-прежнему кривое: код его спасает, но
секрет стоит перезаписать.
