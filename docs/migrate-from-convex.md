# Перенос данных из Convex в bro-next

Скрипт `scripts/migrate-from-convex.ts` переносит людей старого продукта и то,
что им принадлежало, из снимка Convex в Postgres этой установки. Он
идемпотентен: повторный запуск ничего не дублирует, а прерванный прогон
завершается тем, что его просто запускают ещё раз.

## Что переносится

| Convex                                               | bro-next                                                                        |
| ---------------------------------------------------- | ------------------------------------------------------------------------------- |
| `tenants` (`status: "active"`, валидный `phoneE164`) | `user` + `workspaces` + `workspace_memberships` через `ensureVerifiedPhoneUser` |
| `tenants.displayName`                                | `user_profiles.first_name` / `last_name` — только если имя ещё не заполнено     |
| `tenants.tz`                                         | `user_profiles.timezone` — если это известная зона IANA                         |
| `tenants.paidUntil`                                  | `billing_accounts.paid_until` — только если это дата позже уже сохранённой      |
| `payments`                                           | `payments` (`yookassaId` → `id`, сумма, статус, `paidUntilAfter`)               |
| `tenants.telegramUserId` + `telegramChatId`          | `channel_identities` (канал `telegram`)                                         |
| `orders`                                             | `orders` (продавец, номер заказа, название, цена, статус, пункт выдачи)         |
| `vaultItems` + `vaultSecrets`                        | `vault_items` + `encrypted_secrets`, перешифрованные ключом установки           |

## Что не переносится и почему

- **Состояние браузера** (`browser*` поля тенанта, `browserSessions`,
  `browserCharges`). Это ссылки на живые сессии чужого облака: к моменту
  переноса они уже мертвы, а новая установка запускает браузерные поручения
  через другой сервис.
- **`wakeups`, `jobs`, `watchers`.** Напоминания, задачи и подписки на почту и
  календарь завязаны на идентификаторы внешних триггеров старого проекта.
  Перенесённая строка указывала бы в никуда; расписания и наблюдатели
  создаются заново на новой стороне.
- **`files`.** Байты лежат в `_storage` Convex, а не в экспорте таблиц.
- **`sessions`, `loginChallenges`.** Это токены входа. Вход в bro-next выдаёт
  Better Auth, и старые токены в нём недействительны по определению.
- **`testTranscript`, `composioEvents`, `wakeupDeliveries`.** Служебные
  таблицы: дедупликация вебхуков и запись исходящих для тестового тенанта.
- **Номера Photon старого проекта** (`photonAssignedNumber`). Номер принадлежит
  проекту Photon, а не человеку, и в новый проект не переезжает — см. раздел
  `--register-photon`.

## Подготовка

### 1. Мастер-ключ сейфа старого продукта

В репозитории старого продукта, с `CONVEX_DEPLOY_KEY` в окружении:

```bash
npx convex env get BRO_VAULT_KEY
```

Это base64 от 32 байт. Не сохраняйте его в файл и не передавайте через
`--help`-подобные аргументы: скрипт читает его только из переменной окружения
`BRO_VAULT_KEY`. Без него перенос сейфа невозможен; всё остальное переносится
с флагом `--skip-vault`.

### 2. Экспорт Convex

Там же:

```bash
npx convex export --path convex-export.zip
unzip convex-export.zip -d convex-export
```

Внутри — по папке на таблицу, в каждой `documents.jsonl`: по одному документу
на строку, с полями `_id` и `_creationTime`. Скрипт читает только
`tenants`, `payments`, `orders`, `vaultItems` и `vaultSecrets`; отсутствующая
необязательная папка — это просто ноль строк.

### 3. Окружение bro-next

```bash
vercel link          # если проект ещё не связан
vercel env pull .env.local
```

В `.env.local` должны оказаться `DATABASE_URL` и доступ к приватному Blob
(`BLOB_READ_WRITE_TOKEN` или `BLOB_STORE_ID` + OIDC) — оттуда берётся ключ
шифрования установки, которым перешифровывается сейф. Для `--register-photon`
нужны ещё `IMESSAGE_PROJECT_ID` и `IMESSAGE_PROJECT_SECRET`.

## Сухой прогон

```bash
BRO_VAULT_KEY=... node --env-file=.env.local --experimental-strip-types \
  scripts/migrate-from-convex.ts --export ./convex-export --dry-run
```

Сухой прогон расшифровывает каждый секрет сейфа, проверяет его по контракту
новой схемы и читает из базы текущее состояние — но не пишет ничего. Вывод:

```
Dry run: 3 of 3 tenants, vault included.
••••1122      migrated  account=new  profile=firstName+lastName+timezone  paid_until=2026-11-01T00:00:00.000Z  payments=1  orders=1  telegram=linked  vault=2 new/0 existing/0 failed
••••8877      migrated  account=new  profile=firstName+timezone  paid_until=-  payments=0  orders=0  telegram=none  vault=0 new/0 existing/0 failed
••••4433      skipped   account=new  profile=-  paid_until=-  payments=0  orders=0  telegram=none  vault=0 new/0 existing/0 failed
    · the tenant is not active

```

Телефон всегда печатается последними четырьмя цифрами, секреты не печатаются
никогда — включая тексты ошибок, где остаются только имена полей и коды
проверок.

## Реальный прогон

```bash
BRO_VAULT_KEY=... node --env-file=.env.local --experimental-strip-types \
  scripts/migrate-from-convex.ts --export ./convex-export
```

Флаги:

- `--dry-run` — ничего не писать.
- `--only +79210001122` — только эти номера; можно повторять флаг или
  перечислить через запятую. Удобно, чтобы сначала перенести себя.
- `--skip-vault` — не трогать сейф (и не требовать `BRO_VAULT_KEY`).
- `--register-photon` — см. ниже.
- `--via-neon-http` — см. ниже.

Ошибка на одном тенанте не останавливает прогон: она печатается под его
строкой, а код возврата в конце становится `1`, если упал хоть один.

### Доступ к базе

По умолчанию используется обычный клиент проекта (`db/index.ts`, пул TCP через
`pg`). Если с машины наружу открыт только HTTPS — например, из песочницы —
добавьте `--via-neon-http`: скрипт выставляет `DATABASE_DRIVER=neon-http`, и
`db/index.ts` собирает Drizzle поверх HTTP-драйвера `@neondatabase/serverless`.
Сервисы при этом не меняются, продакшн — тоже: без этой переменной всё
работает как раньше.

У HTTP-драйвера нет интерактивных транзакций: каждый запрос — отдельный HTTP
вызов, и обернуть перенос одного человека в одну транзакцию нельзя. Поэтому
перенос устроен иначе: каждый шаг идемпотентен сам по себе и адресует строку
естественным ключом.

| шаг                            | ключ идемпотентности                                       |
| ------------------------------ | ---------------------------------------------------------- |
| аккаунт и рабочее пространство | номер телефона (`user.phoneNumber`)                        |
| профиль                        | имя пишется только если его нет; зона — значение из Convex |
| `paid_until`                   | обновляется только если новое значение позже текущего      |
| платёж                         | `id` платежа YooKassa                                      |
| заказ                          | `workspace_id` + продавец + номер заказа                   |
| Telegram                       | канал + внешний идентификатор пользователя                 |
| элемент сейфа                  | `label` + `kind` внутри рабочего пространства              |

Отсюда же следствие: если человек уже завёл в bro-next элемент сейфа с таким же
названием и того же вида, перенос его не тронет и посчитает как `existing`.

### Что может не перенестись

Новый контракт сейфа строже старого, и скрипт не выдумывает недостающие
значения, а сообщает о них:

- карта без `billingPostalCode` — в новой схеме почтовый индекс обязателен;
- адрес без региона или индекса — там же обязательны оба;
- битый шифротекст или payload, не совпадающий со старым контрактом.

Такой элемент считается `failed`, остальные данные человека при этом
переносятся. Дальше — либо попросить человека добавить карту заново в
кабинете, либо поправить исходные данные и перезапустить перенос: уже
перенесённое повторно не создастся.

## `--register-photon`

Номера Photon старого проекта не переезжают: номер выдан тому проекту, и в
новом проекте у человека будет другой, американский (+1). С флагом
`--register-photon` скрипт заводит для каждого номера shared-пользователя в
**новом** проекте Photon и сохраняет выданный номер в `onboarding_requests`.
Выданный номер печатается в строке тенанта — это не секрет, его и нужно
сообщить человеку.

Повторный запуск номер не покупает заново: если для телефона уже есть запись в
`onboarding_requests`, берётся она.

## Порядок переключения

1. Прогнать `--dry-run` на полном экспорте и разобрать всё, что помечено
   `failed` или `skipped`.
2. Прогнать перенос по-настоящему (при необходимости частями через `--only`).
3. Прогнать `--register-photon` и разослать людям их новые номера; до этого
   момента старый деплой ещё отвечает на старом номере.
4. Убедиться, что люди пишут на новый номер и всё на месте: оплата, заказы,
   сейф.
5. Выключить старый деплой Convex (`npx convex deployments`, затем отключение
   продакшн-деплоя в дашборде) и отозвать `BRO_VAULT_KEY`.

Между шагами 2 и 5 данные существуют в обеих системах. Всё, что человек сделал
в старом продукте после экспорта, в новый не попадёт — поэтому между экспортом
и переключением стоит держать паузу как можно короче, а при длинной паузе
сделать экспорт ещё раз и повторить перенос: он идемпотентен.
