# Кошелёк Бро на МОНЕТА.РУ

Состояние на 20.10.2026: план, договора с НКО «МОНЕТА» нет, кода в Бро нет —
только проба API `scripts/moneta/probe.sh`. Решение владельца 20.10: делать
вариант «Бро — платформа» с быстрым онбордингом.

## Зачем

Кошелёк ЮMoney (`docs/dev-notes.md`, «Кошелёк ЮMoney») не закрывает:

- **перевод человеку по номеру телефона в любой банк** — у ЮMoney переводы
  только на кошельки ЮMoney. У Монеты это СБП C2C Push, и до оплаты она
  отдаёт ФИО получателя: Бро может спросить «Мария Ивановна К., верно?»;
- **платежи в бюджет по реквизитам** (налоги, штрафы по УИН) — оплата по ИНН
  через API ЮMoney не открывается (витрина 5551);
- **пополнение кошелька из своего банка по СБП** без карты и 3-D Secure.

## Модель: Бро — платформа

OAuth к кошельку, который у человека уже есть, у Монеты нет: все API — для
организации по договору. Поэтому ИП или ООО владельца заключает с НКО договор
об информационно-технологическом взаимодействии (ИТВ), регистрирует человеку
электронный кошелёк (ЭСП) «МОНЕТА» и платит с него через MerchantAPI сам —
платёжный пароль кошелька задаёт платформа (`CreateAccountRequest`).

Делегированный доступ к чужому счёту в API есть (`SaveAccountRelation`: права
`canViewAccount`, `canEditAccount`, `canProcessOperation` пользователю по
почте, нужен платёжный пароль владельца), но чьим паролем платит получивший
доступ и открыт ли MerchantAPI обычному кошельку — не описано. На него не
рассчитываем.

Юридически Бро здесь — платформа, через которую идут деньги людей, а не
помощник с доступом: до регистрации человека платформа обязана показать
Соглашение ЭСП и лимиты и получить согласие на обработку персональных данных
(`/solutions/marketplaces/registration/individual/`).

## API по документации

Источники: docs.moneta.ru (HTML) и спецификация
`docs.moneta.ru/_documents/Moneta.MerchantAPI.v2.ru.pdf` (09.2022, 358 стр.;
WebFetch текст PDF не достаёт — `pdftotext -layout`). Вживую проверен только
вход: неверная пара на demo отвечает 400 и `faultDetail` 300.1.

- **Транспорт.** SOAP или JSON-конверт той же формы:
  `POST https://service.moneta.ru/services` (тест —
  `https://demo.moneta.ru/services`), `Content-Type: application/json;charset=UTF-8`;
  метод — ключ `<Метод>Request` в `Envelope.Body`, вход — в
  `Envelope.Header.Security.UsernameToken`. Логин и пароль — от личного кабинета; есть вход
  клиентским сертификатом x509 (`https://service.moneta.ru:8443/services/x509`).
  Атрибуты счёта и SMS-пароль видны лишь с `"version": "VERSION_2"`.
- **Регистрация человека.** `CreateProfileRequest` (`profileType` `CLIENT`,
  `email_for_notifications` обязателен, `cell_phone` можно передать с
  `approved: true`, если телефон уже подтвердила платформа) →
  `CreateProfileDocumentRequest` (`PASSPORT`, серия и номер) →
  `ApprovePhoneSendConfirmationRequest` / `ApprovePhoneApplyCodeRequest` →
  `AsyncRequest` с `SimplifiedIdentificationRequest` (УПРИД через СМЭВ, «обычно
  в течение часа», ИНН Монета берёт из ФНС; нет callback 700 минут —
  `GetProfileInfoRequest`) → `CreateAccountRequest` (`prototypeAccountId`,
  `paymentPassword`). URL-уведомления `CREATE_UNIT`, `CREATE_DOCUMENT`,
  `CREATE_ACCOUNT`. Новый профиль — в группе «Анонимные пользователи».
- **Идентификация без ввода паспорта — MonetaID** (`/monetaid/`): виджет
  `https://mid.moneta.ru/identification` (тест `mid.demo.moneta.ru`),
  провайдеры `tid`, `mts`, `esia`, `uprid`; запрос и `statusURL` подписаны
  HMAC-SHA512 ключом `apiSecret` партнёра. Нужен договор ИТВ и «установление
  доверия» в кабинете партнёра.
- **Платёж.** `VerifyPaymentRequest` (проверка, без списания) →
  `GetAccountPaymentPasswordChallengeRequest`, если пароль SMS →
  `PaymentRequest` (`payer`, `payee`, `amount`, `isPayerAmount`,
  `paymentPassword`, `clientTransaction`, `operationInfo`). `Transfer`
  устарел. Статус — `GetOperationDetailsById`, история —
  `FindOperationsList`, `FindLastOperationsList`. Тип платёжного пароля
  счёта: `STATIC`, `SMS_SIMPLE`, `SMS_SESSION`, `TOTP_RFC6238`.
- **Услуги и бюджет.** `PaymentRequest` на счёт провайдера (`payee`) с полями
  в `operationInfo`; банковский перевод — `payee` 5 с `WIREUSERNAME`,
  `WIREUSERINN`, `WIREBANKACCOUNT`, `WIREBANKBIK`, `WIREKBK`, `WIREOKTMO`,
  `WIREDOCINDEX` (УИН). Каталога провайдеров в API нет: спецификация велит
  провести платёж в кабинете и взять `operationInfo` из
  `GetOperationDetailsById`. Её таблица выводов устарела (Яндекс.Деньги,
  WebMoney, Деньги@Mail.ru). Коды ошибок `500.4.*` — поиск начисления в ГИС
  ГМП по УИН, ЕПД ЖКХ, лицевой счёт в реестре начислений, ОСАГО: инфраструктура
  есть, как её звать — вопрос к Монете.
- **СБП C2C Push** (`/sbp/c2c-me2me-push/`, `/sbp/get-participants/`):
  `GetNextStepRequest` с `providerId` 354 по стадиям
  `SECUREDFIELD:payment_stage`: 1 — телефон `CUSTOMFIELD:idPo_20` и счёт
  списания `SECUREDFIELD:nbsOt_30`; 2 — по `SECUREDFIELD:unsBo_79` список
  банков и «банк по умолчанию» (`SECUREDFIELD:idBp_24`); 3 — банк и сумма
  `SECUREDFIELD:sumOpSbp_44`; 4 — ФИО `CUSTOMFIELD:pamPo_74`. Затем
  `PaymentRequest` с `payee` 354 между `SECUREDFIELD:minTime` и
  `expirationTime` (≈ 3 минуты); финальный статус — за 10 с. Список банков —
  на каждый перевод.
- **СБП Me2Me Pull** (`/sbp/c2c-me2me-pull/`): пополнение из своего банка.
  `GetNextStepRequest` 374.2 со `scenarios` `Me2MePull` → `InvoiceRequest`
  (`payer` 374, банк в `SECUREDFIELD:SBPBANKID`); счёт в банке появляется за
  7 с, оплатить — за 10 минут. Распоряжение в банке может быть «на все
  последующие переводы» — дальше без подтверждения. Кошелёк получателя —
  только после УПРИД или полной идентификации.
- **Регулярные платежи** — `CreateOperationTemplateRequest` с типом `REGULAR`
  (автоплатёж на стороне Монеты).

## Онбординг

Цель — пара минут и одна страница, как `/yoomoney/<id>` (`docs/dev-notes.md`,
«Онбординг кошелька»):

1. Просьба в чате («переведи Маше 500») → Бро: нужен кошелёк, кнопка.
2. Страница: Соглашение ЭСП и лимиты Монеты, согласие на персональные данные,
   почта (у входа по телефону почта синтетическая — `phone-…@local-vault.invalid`).
3. Телефон: вошёл в Бро по номеру — передаём `approved: true`, без SMS; иначе
   код на той же странице.
4. Личность: кнопка T-ID / Госуслуги (MonetaID); запасной путь — паспорт и
   ИНН или СНИЛС (УПРИД), Бро пишет в чат, когда проверка прошла.
5. Кошелёк создаётся сразу. До проверки личности нельзя пополнение из банка
   (документация) и платёж в бюджет по реквизитам (проба 20.10, ниже); про
   переводы людям и услуги — не проверено.
6. Пополнение по СБП из своего банка с распоряжением на последующие
   переводы: первый раз — подтверждение в приложении банка.

## Безопасность — решить до кода

- Логин платформы открывает кошельки всех людей: вход — сертификатом, не
  паролем. `/etc/bro/env` видят инструменты модели (`docs/dev-notes.md`,
  «eve»): где держать ключ платформы и платёжные пароли — отдельное решение.
- Платёжные пароли кошельков — шифровать, как образцы подписей
  (`person_signatures`, AAD воркспейс+пользователь).
- Платит Бро по тем же правилам, что ЮMoney: одно «да» — один платёж
  (`consent_hash`), лимит трат (`spend_limit`), прямая покупка.
- Паспорт, ИНН и СНИЛС идут через Бро в Монету: Монету — в
  `agent/lib/privacy/facts.ts` и `app/(public)/privacy` (правятся вместе).

## Вопросы к Монете

1. Доступен ли MerchantAPI владельцу обычного кошелька, есть ли в кабинете
   настройка делегированного доступа и чьим платёжным паролем платит
   получивший доступ.
2. Переводы C2C Push с кошелька, созданного платформой: лимиты, комиссии,
   нужна ли упрощённая идентификация; что доступно анонимному кошельку.
3. Провайдеры: актуальный список (связь, ЕПД ЖКХ, ГИС ГМП по УИН, СТС и ВУ,
   налоги) и поля формы провайдера через API (`GetNextStep`,
   `services-providers.wsdl`).
4. Договор ИТВ для платформы с кошельками физлиц, тарифы, тестовый доступ
   с правами платформы, значения `prototypeAccountId`, группы профиля и
   счёта списания в СБП.

## Тестовый контур

- `https://demo.moneta.ru/register.htm` — регистрация пользователя открыта
  (телефон, почта, пароль, капча, затем платёжный пароль). Счета demo и
  прода разные. Виртуальные деньги на счёт пользователя и подтверждение
  кабинета магазина даёт поддержка PayAnyWay (`business@support.payanyway.ru`)
  по почте или телефону регистрации (`/assistant/v1/starting/`).
- Проба — один метод MerchantAPI; прокси облачной сессии иногда рвёт
  соединение с demo.moneta.ru, и проба повторяет только несостоявшееся:

  ```sh
  MONETA_LOGIN=… MONETA_PASSWORD=… scripts/moneta/probe.sh \
    FindAccountsListRequest '{"version":"VERSION_2"}'
  ```

Проба 20.10 обычным пользователем demo (анонимный кошелёк, баланс 0, без
договора):

- Вход в MerchantAPI логином и паролем кабинета работает:
  `FindAccountsListRequest` — счета RUB (основной), USD, EUR, платёжный пароль
  `STATIC`; `GetProfileInfoRequest` без `unitId` отдаёт свой профиль.
- Прав платформы нет: `CreateProfileRequest` (`client`) — 300.4.5 «Запрещено
  создавать профиль с указанным типом»; `FindAccountRelationsRequest` своего
  счёта — 300.2 «Access is denied».
- СБП: список банков Me2Me Pull (`GetNextStepRequest` 374.2, `scenarios`
  `Me2MePull`) — 266 банков. C2C Push, стадия 1 (354) — 400.1.12
  «Недостаточно средств для перевода»: баланс проверяется до поиска банка.
- `VerifyPaymentRequest`: `payee` 354 требует `unsBo_79` (сначала стадии
  `GetNextStep`); 9000 (водоканал из примера спецификации) — «Лицевой счет»;
  5 (банковский перевод с КБК и УИН) — 500.6.1.33 «Вывод на данный счет
  запрещен для анонимных пользователей»; 1144 (CyberPlat) — 500 «Ошибки в
  конфигурации получателя».
- Проверка платежа в бюджет и Me2Me Pull ждут идентифицированного кошелька,
  перевод C2C — денег на счёте.
