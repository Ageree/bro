# A3 — Login / Cloud profile / live-view / vault card payment audit

Repo: /home/user/bro. Read-only audit, no files modified.

## 1. Summary

The login/pay slice has one architecture that works well when everything happens inside a *single* model turn (vault login bound as `secretBindings`, CDP-open the login page, wait synchronously up to 45 s, text the live-view link). It falls apart exactly where the owner said it hurts: across turns and across the async follow-through/wakeup boundary.

The three worst holes:

1. **An errand (not `profile_setup`) that stalls on OTP/login mid-task has no reliable way to ever reach the human.** The Convex background poller (`pollRun`) only sends a live-view link for tasks marked `[bro-login]`; a plain `browser_task` errand's stored task is the raw human text and is never so marked, so `shouldSendLoginLink` never fires for it. The one background-wakeup prompt that *could* surface it explicitly tells the model to answer `[SILENT]` when the job is "still running and nothing to inject" — exactly the OTP-wait state. The only chance the link is ever surfaced is the same-turn synchronous window, which is capped at 2 s (`BROWSER_WAIT_MS`). This is the exact "lost OTP code" / "dead end" failure the product brief calls out, and it's structural, not occasional.
2. **`profile_setup` has no idempotency guard.** Unlike `browser_task` (`nextBrowserAction`), every call to `profile_setup` — including the retry it itself tells the model to make when `status:"pending"` — starts a brand-new Browser Use run/browser and re-charges the monthly quota, abandoning whatever run/live-link was already in flight.
3. **Cross-tenant profile sharing risk.** If `BROWSER_USE_PROFILE_ID` is set, `createProfile` is *never* called for any tenant that doesn't already have a personal `browserProfileId` — every such tenant is silently handed the same shared Browser Use Cloud profile (same cookies, same logged-in accounts, same history) forever. Contrast with the Kernel/worker path, which explicitly hashes the phone number specifically so this can't happen.

Runner-up but still severe: a 3-D Secure stop is effectively a dead end (run ends terminal, follow-through is cancelled, nobody tells the human what to say afterward, and nothing resumes the purchase); `maybeRecordOrder` only sees `paying:true` on the very first synchronous call of `browser_task`, so a purchase that finishes on a later poll/wakeup (the common case) is recorded only if the *original* task text happens to match a "buy" verb regex.

## 2. Findings

### F1 — P0 — Errand-time OTP/login stalls never reach the human automatically
**File/lines:**
- `convex/browserFollow.ts:262-273` — `const loginWait = isLoginWaitTask(tenant.browserTask);` and the `needLoginHydrate` branch.
- `convex/lib/browserLivePolicy.ts:301-312` — `shouldSendLoginLink` requires `opts.loginWait`.
- `convex/lib/browserProfilePolicy.ts:11-13` — `isLoginWaitTask` only matches a task string that starts with `[bro-login]` (`LOGIN_MARK`).
- `agent/tools/browser_task.ts:79-87` — `persist()` stores `browserTask: task`, i.e. the **raw** human errand text (e.g. `"вызови такси до аэропорта"`), never wrapped with `LOGIN_MARK` (that wrapping only happens transiently inside `scaffoldTask`/`startRun`, and is not what gets persisted).
- `agent/channels/imessage.ts:701-702` — the `kind === "browser_poll"` wakeup prompt: *"Если completed — отправь результаты. Если failed или джоб завис — скажи. Если ещё работает и инжектить нечего — ответь `[SILENT]`."* No branch for "still running, `liveUrl` present, needs login."
- `agent/lib/browser-policy.ts` `BROWSER_WAIT_MS = 2_000` — the only synchronous window in `browser_task.ts:621-625` where the tool's own return payload (which does carry `liveUrl`, see `browser_task.ts:89-104`) could be seen by the model in the same turn.

**What happens:** Tenant with no vault login/no cookies says "вызови такси". `browser_task` starts a run, waits 2 s, almost certainly still running, replies "ищу…". Convex `browserFollow` starts polling every 2 min. The Cloud agent reaches «Войти», needs phone+SMS, and just sits (per `errandLoginBlock` in `agent/lib/browseruse.ts:137-150`, it's told to stop and give live-URL only once it truly cannot proceed — until then the run legitimately stays `running`). Every `pollRun` call computes `loginWait = isLoginWaitTask(tenant.browserTask)` — false, because `browserTask` is `"вызови такси до аэропорта"`, not `"[bro-login]\n…"`. So `shouldSendLoginLink` is never true and the Convex side never sends anything. Eventually `nextFollowDecision` (`convex/lib/browserFollowPolicy.ts`) fires the `wakeupAgent` action with the generic `browser_poll` prompt, whose own text tells the model to say `[SILENT]` for "still running, nothing to inject" — which is precisely this state, even though `browser_task`'s own payload (re-fetched by the model on that turn) contains `liveUrl`. Net effect: no automatic message ever reaches the human; the only way out is the human proactively pinging ("ну что") *and* the model, on its own initiative, noticing `liveUrl` in the tool result against the grain of the wakeup instructions it was just given.
**Why:** the "is this a login-wait task" signal is purely string-marker-based and only exists for `profile_setup`'s dedicated `loginWaitTask`/`loginVaultTask`; ordinary errands never get that marker persisted, so every login-link-sending code path that gates on it (`shouldSendLoginLink`) is blind to errand-time logins. The wakeup prompt then actively suppresses the one place that *does* have the live URL.
**Fix:** (a) persist a `browserNeedsLoginSince`/`browserLiveNeedsLogin` flag (or just stop requiring the `[bro-login]` marker and instead gate `shouldSendLoginLink` on "no `browserLoginLinkSentAt` yet AND `liveUrl` present AND run not yet terminal", regardless of task shape); (b) add an explicit branch to the `browser_poll` wakeup prompt in `agent/channels/imessage.ts`: if the tool result carries an unsent `liveUrl`, say so and give the link instead of `[SILENT]`.
**Check script:** extend `scripts/browser-policy-check.ts` (or a new case in `profile-sync-check.ts`) asserting `shouldSendLoginLink`/its errand-path equivalent fires for a plain errand task, and grep-assert the wakeup prompt text handles a `liveUrl`-present case.

### F2 — P0 — `profile_setup` has no run-reuse guard; every retry starts a fresh browser and re-charges quota
**File/lines:** `agent/tools/profile_setup.ts:186-201` (billing gate runs on every call), `:203-216` (vault path always calls `startRun` with no session/runId reuse), `:246-252` (wait path: same), `:279-287` (`status:"pending"` hint literally says *"вызови profile_setup ещё раз с тем же url"* with no cap or reuse check).
**What happens:** `waitForLoginLanding` (45 s) times out without landing → tool returns `status:"pending"` and tells the model to call `profile_setup` again with the same URL. The model (or an impatient human re-asking) does so. `profile_setup` has no check of `tenant.browserRunId`/`browserStatus` before starting — it unconditionally creates a new Browser Use run (`startRun(task, undefined, …)`, `sessionId` always `undefined`) and overwrites `tenant.browserRunId`/`browserSessionId`/`browserLiveUrl` via `persistRun`. The previous run/browser is abandoned (not cancelled), and if a live-view link had already been sent from an earlier attempt, that link is now stale/dead while the human may be mid-login on it. Compare `agent/tools/browser_task.ts:462-480`, which has `nextBrowserAction` precisely to avoid this ("never a second search while one runs").
**Why:** `profile_setup` was written before/independently of the `nextBrowserAction` poll/reuse pattern and has no equivalent.
**Fix:** before starting a new run, check `tenant.browserRunId` + `browserStatus` (active) and the persisted task's URL; if a login run for the *same page* is already in flight, poll/hydrate it instead of starting a new one (mirror `nextBrowserAction`/`waitForRun`).
**Check script:** add a case to `scripts/profile-sync-check.ts` that calls the equivalent of `nextBrowserAction`-style logic (once extracted) with an active `browserRunId` for the same login page and asserts "poll", not "start".

### F3 — P0 — Cross-tenant profile sharing via `BROWSER_USE_PROFILE_ID`
**File/lines:** `agent/lib/browseruse.ts:169-173` (`envSyncedProfileId`), `agent/tools/profile_setup.ts:130` (`tenant.browserProfileId ?? envSyncedProfileId()`), `agent/tools/browser_task.ts:385` (`resolveSyncedProfile`, same pattern).
**What happens:** if `BROWSER_USE_PROFILE_ID` is set in the deployment env, `profileId` is truthy for *every* tenant that hasn't already had its own `browserProfileId` written, so `createProfile(phone)` (which would mint a distinct per-tenant profile) is **never called**. Every such tenant is then persisted (`browserProfileId: profileId`) onto the *same* shared Browser Use Cloud profile — same cookies, same logged-in shop/taxi accounts, same saved addresses/order history — indefinitely. Tenant B's errand could ride on tenant A's logged-in Ozon session, or vice versa.
**Why:** the fallback was presumably meant as a one-time "seed with an already-signed-in dev/owner profile" convenience, but nothing scopes it to a single tenant or clears it once a personal profile should take over.
**Fix:** either remove the env fallback entirely (each tenant always gets its own `createProfile`), or scope it explicitly to one designated owner phone (e.g. compare `phone === process.env.BRO_OWNER_PHONE` before using the shared id) and always call `createProfile` for every other tenant.
**Check script:** new case in `scripts/profile-sync-check.ts`: with `BROWSER_USE_PROFILE_ID` set and two different tenant rows with no `browserProfileId`, assert `createProfile` gets called for the second tenant (or that they end up with different ids) rather than both reusing the env value.

### F4 — P0 — 3-D Secure stop is a true dead end
**File/lines:** `agent/lib/browser-pay.ts:137` (`payScaffold`: *"3-D Secure … остановись и дай live-URL"* — instructs only the Cloud agent), `agent/tools/browser_task.ts:326-372` (`settle`: `isTerminal(run.status)` → cancels `browser_poll` wakeup *and* the follow-through workflow), `convex/browserFollow.ts` (no re-arming once cancelled).
**What happens:** Cloud agent hits 3DS, ends its turn with the live-URL instruction — the Browser Use run's `status` goes terminal (`completed`) from the API's point of view. `settle()` sees `isTerminal` and calls `cancelWakeup` + `cancelBrowserFollow` — follow-through is fully torn down, not paused. The human opens the live view and completes 3DS. Nothing in the product ever tells them to say "готово"/"оплатил" afterward (no such copy exists anywhere in `browser-pay.ts`, `profile_setup.ts`, or `instructions.md`), and even if they do say something, it only gets picked up if it happens to match `injectCandidate` (`convex/lib/browserInjectPolicy.ts`) — a code-like string, a wait-phrase, or a correction phrase. "Готово"/"оплатил"/"сделал" match none of `isChatCodeMessage`, `isWaitInject`, or `looksLikeCorrectionText`. So unless the human's message happens to look like an OTP digit string, nothing resumes the purchase, and no order gets recorded (the run that "completed" did so before the payment was actually confirmed, so `maybeRecordOrder`'s `parseOrderFromResult` has nothing to parse a real order out of anyway).
**Why:** the whole follow-through/inject machinery is built around either "run still active" or "human sends something injectable"; a human confirming an out-of-band action (3DS in a live tab) with a plain acknowledgement is not modeled at all.
**Fix:** (a) add a short, explicit line to the live-URL chat text for the pay case ("после подтверждения в банке напиши «готово», и Bro закончит покупку") — this needs a pay-specific chat text, not just `payScaffold`'s agent-facing copy; (b) add "готово"/"оплатил"/"сделано" as a recognized `injectCandidate` kind (e.g. a `"resume"` kind) that re-queues into the session even when the run already went terminal, spawning a fresh run in the same session to verify/finish the order.
**Check script:** new assertions in `scripts/browser-pay-check.ts` for a "resume after 3DS" chat phrase, plus a new case in `scripts/browser-inject-check.ts` (if that's the injection check) for the "готово" family.

### F5 — P0 — `maybeRecordOrder` loses `paying` on every path except the very first synchronous call
**File/lines:** `agent/tools/browser_task.ts:304-324` (`maybeRecordOrder`: `if (extra.paying !== true && !taskLooksLikeBuy(task)) return;`), `:638-640` (only the fresh-"start" branch sets `paying: true, payAccount, payHosts` in `extra`), `:473-480` (reuse branch: `extra = { reused: true }`, no `paying`), `:482-502` (poll branch: `extra = { polled: true, … }`, no `paying`), `:277-289` (`maybeInjectChat`'s own `settle()` call: `extra` has `injected/typed/submitted/alreadyNotified/hint`, no `paying`). No tenant field persists "this run is a paid run" (`convex/schema.ts:18-30` has no `browserPaying`/`browserPayHosts`).
**What happens:** a paid errand almost never actually completes inside the initial 2 s synchronous window (`BROWSER_WAIT_MS`) — the realistic path is: start → still running → follow-through/poll/inject cycles → eventually `completed`. Every one of those later paths calls `settle()` with an `extra` that has **no** `paying` field, so `maybeRecordOrder` falls back to `taskLooksLikeBuy(task)` (`agent/lib/purchase-policy.ts`'s `BUY` regex on `купи|закаж|оплати|выкупи|бери|возьми|оформи`). A task like `"вызови такси до аэропорта"` paid with a bound card never matches `BUY`, so **no order row is ever written**, even though money moved. `list_orders` then shows nothing and the model either invents an answer or tells the human incorrectly that there's no record.
**Why:** `paying` is a call-scoped local (`payOpts`), never round-tripped through `tenant.browserTask`/persisted state, so any settle() that isn't the original call has no way to know the in-flight run was a paid one.
**Fix:** persist `browserPaying: boolean` and `browserPayHosts: string[]` alongside `browserTask` in `setBrowser`/`persist()` when a paid run starts, and read them back into `extra` on every branch (`reuse`, `poll`, `maybeInjectChat`'s settle) before calling `maybeRecordOrder`.
**Check script:** `scripts/orders-check.ts:177,180` currently only greps the *source text* for `"extra.paying"` — it does not exercise the poll/reuse/inject code paths at all. Add a behavioral case: simulate a poll-branch `settle()` call for a completed paid taxi run and assert an order gets recorded.

### F6 — P0 — Vault login is not bound for a keyword-only errand (taxi/WB/Ozon) with no explicit URL
**File/lines:** `agent/tools/browser_task.ts:563-572` (`loginPages` built from `payHosts` + URLs regex-matched out of `task` text only) vs `:575` (`const startPage = errandStartUrl(task);` — computed **after** `loginPages`/`vaultLogin` are already resolved). `convex/lib/browserStartPolicy.ts:19-33` (`errandStartUrl` resolves `"такси"` → `https://taxi.yandex.ru/`, `"озон"`/`ozon` → ozon.ru, `"вб"`/wildberries → wb.ru from wording alone, no URL needed).
**What happens:** Human says "вызови такси" with a saved vault login (`kind:"login"`, origin `https://taxi.yandex.ru`) and no card payment involved. `payHosts` is `undefined` (no `pay`), and the task text contains no `https://` URL, so `loginPages` is `[]` → `vaultPasswordLoginForPages(phone, [])` returns `undefined` → `secretBindings` is never populated with the saved Yandex login, even though `errandStartUrl("вызови такси")` (computed two lines later, unused for this purpose) would have resolved the exact same taxi.yandex.ru URL that could have looked the login up. The Cloud agent then only gets the generic `errandLoginBlock` (type from task text if present, else stop and ask for live-URL) — it never gets to type the saved password via `secretBindings`.
**Why:** ordering bug — `startPage` is computed strictly after the vault-login lookup that could have used it.
**Fix:** move `const startPage = errandStartUrl(task);` above the `loginPages` construction and add it to the array passed to `vaultPasswordLoginForPages` (e.g. `[...(payHosts ?? []).map(h=>`https://${h}`), ...(startPage ? [startPage] : []), ...task.match(...)]`).
**Check script:** add a case to `scripts/vault-check.ts` or `scripts/browser-pay-check.ts`: given a vault login with origin `https://taxi.yandex.ru` and task `"вызови такси домой"` (no URL, no pay), assert the resulting `secretBindings`/`vaultLogin` is non-empty.

### F7 — P1 — Cookie-covers-page cache is never revalidated or invalidated
**File/lines:** `agent/tools/profile_setup.ts:143-157` (`cookieDomains` only re-fetched via `getProfile` when currently `.length === 0`), `agent/tools/browser_task.ts:393-399` (same pattern in `resolveSyncedProfile`), `convex/lib/browserProfilePolicy.ts:153-178` (`cookieDomainsCoverPage`) and `:108-111` (`alreadyLoggedChatText` — *"Вход уже сохранён"*).
**What happens:** once `browserCookieDomains` is non-empty for a tenant, it is cached on the tenant row and never refreshed (the refresh-if-empty guard only fires the *first* time). If those cookies are actually a stale/guest/logged-out session (a real possibility — the code's own comment and instructions text explicitly says "куки ≠ вход"), `profile_setup` will keep replying `alreadyLoggedChatText` ("вход уже сохранён", no live-view sent) on every future call for that domain, permanently, with no feedback loop from any later run's actual result (e.g. Cloud agent reporting "ещё не вошёл" / needing to click «Войти» again) back into clearing `browserCookieDomains` or `browserProfileSyncedAt`.
**Why:** the only "already logged in" signal is presence of a cached cookie-domain list; there is no code path that listens to a run's outcome (`isLoginWaitTask` "ещё не вошёл", or an errand hitting the guest wall) and invalidates that cache.
**Fix:** when a run (login-wait or errand) finishes with a "not actually logged in" signal (e.g. loginWaitTask's own `"ещё не вошёл"` result, or an errand's `errandLoginBlock` guest-detection), clear/patch `browserCookieDomains` (or at least `browserProfileSyncedAt`) so the next `profile_setup` call re-checks via `getProfile` instead of trusting the stale cache.
**Check script:** extend `scripts/profile-sync-check.ts` with a case: given cached `cookieDomains` that cover the page but a run result containing "нужен вход"/"ещё не вошёл", assert some policy function flags the cache as stale.

### F8 — P1 — Phone number sent to Browser Use Cloud as profile `userId`/`name`
**File/lines:** `agent/lib/browseruse.ts:213-221` (`createProfile`: `body: JSON.stringify({ userId, name: userId })` where the caller passes `phone` directly — see call sites `agent/tools/profile_setup.ts:133` and `agent/tools/browser_task.ts:388`). Compare `agent/subagents/worker/lib/kernel.ts:32-39` (`profileNameForTenant`: *"Stable, non-reversible profile name. The phone number never reaches Kernel."* — SHA-256 hash, tested in `scripts/worker-check.ts:25-32` to explicitly assert the phone never appears in the name).
**What happens:** the tenant's E.164 phone number is sent verbatim, twice (as `userId` and as the human-readable `name`), to a third-party vendor (Browser Use Cloud), where it likely surfaces in their dashboard/support tooling/logs. The sibling Kernel integration deliberately avoids exactly this by hashing.
**Why:** oversight/inconsistency between the two browser-vendor integrations; no equivalent of `profileNameForTenant` exists for Browser Use Cloud.
**Fix:** add a `profileNameForTenant`-style hash helper for Browser Use Cloud and pass that instead of the raw phone in `createProfile`.
**Check script:** add a case to `scripts/profile-sync-check.ts` mirroring `scripts/worker-check.ts:25-32` — assert the value passed to `createProfile`/the request body never contains the raw phone digits.

### F9 — P1 — Login attempt burns browser-job quota even before any errand runs
**File/lines:** `agent/tools/profile_setup.ts:186-201` (`countBrowserJobStart`/`browserGateFromResult` called unconditionally, even for the vault-login and login-wait paths that aren't an "errand" at all), `convex/tenants.ts:924-931` (`countBrowserJobStart` mutation — one call = one charge via `chargeBrowserJob`).
**What happens:** every `profile_setup` invocation (including each retry per F2) consumes one of the tenant's monthly `browserJobsPerMonth` allowance, before any actual errand (WB/Ozon/taxi) has even started. A tenant who needs three `profile_setup` retries to get logged in (not unlikely given F2's lack of a landing/reuse guard) has burned three job-months' worth of quota on login alone.
**Why:** `profile_setup` reuses the exact same billing gate as `browser_task` with no distinction between "just signing in" and "doing an errand", and (per F2) has no dedupe to stop it from being charged multiple times for what is conceptually one login attempt.
**Fix:** either don't charge quota for `profile_setup` at all (login is prerequisite infrastructure, not an errand), or charge at most once per login attempt (tie the charge to `sameBrowserRun`/an existing in-flight login the way F2's fix would).
**Check script:** `scripts/purchase-check.ts` / a billing-focused check — assert `profile_setup`'s billing gate is not re-charged when retried against an in-flight login run.

### F10 — P1 — Raw Cloud `result` text is not scanned for secrets before reaching the model
**File/lines:** `agent/lib/browseruse.ts:495-499` (`hydrate`: `result = pick(run, ["result","output"]) ?? …` — no scrubbing), `agent/tools/browser_task.ts:89-104` (`payload()`: `result: run.result ?? null` passed straight through to the tool's return value, which the model sees and is told to "paste those results"). Compare `agent/lib/order-policy.ts:136-138` (`stripSecrets` — strips PAN-like digit runs) which **is** applied, but only inside `parseOrderFromResult` (used solely to build the `orders` table row via `maybeRecordOrder`), not on the copy of `result` the model/human actually see.
**What happens:** `loginScaffold()`/`payScaffold()` tell the Cloud agent *"Никогда не читай, не переписывай и не запоминай значения этих полей"* — a soft, LLM-compliance-only instruction. If the Cloud agent's own final `result` text nonetheless echoes something typed (a card number, a password, an OTP it read off-screen), there is no server-side filter on Bro's side catching it before it's hydrated into `BrowserRun.result` and returned to the model (and potentially relayed verbatim to the human in chat).
**Why:** `stripSecrets` exists but was wired only into the order-parsing helper, not into the primary `hydrate()`/`payload()` path.
**Fix:** apply the same (or a stronger, password-aware) scrub to `run.result` inside `hydrate()` before it's stored/returned, not just inside `parseOrderFromResult`.
**Check script:** add a case to `scripts/browser-pay-check.ts` or a new `scripts/browseruse-check.ts`: feed a synthetic Cloud `result` containing a 16-digit PAN and assert the value returned from `hydrate`/`payload` no longer contains it.

### F11 — P2 — No persisted "pending errand" across the login/OTP/3DS detour
**File/lines:** no code reference — confirmed by absence: `convex/schema.ts` tenant fields (`:5-59`) have nothing like `pendingErrandTask`; `agent/instructions.md:74` (*"`already` / `usedProfile` / `usedVault` / «вошёл» → сразу `browser_task`"*) relies entirely on the model recalling the original errand text from conversation history.
**What happens:** after `profile_setup` finishes (vault login, cookies-already-cover, or live-view login done), nothing in the code hands the model back the original errand ("вызови такси до аэропорта") to resume — that's purely up to the model still having it in its context window. For a long OTP wait, a multi-day pause, or any context compaction, the original ask could be lost, and Bro has no durable record to fall back on (contrast with the `job_open`/`job_wait` framework the product explicitly has for "browser running" waits per `instructions.md:98`, which nothing in `profile_setup`/`browser_task` actually calls).
**Why:** the login/live-view flow was built independently of the jobs framework; nothing bridges them.
**Fix:** either have `profile_setup`/`browser_task` open a `job` row (goal = original errand text, `waitingFor:"browser"`) when a login/live-view detour starts, or persist the original errand text on the tenant row alongside `browserTask` so a resume after login can be code-driven instead of memory-driven.
**Check script:** n/a today (no existing check covers jobs↔browser integration) — would need a new `scripts/jobs-check.ts` case.

### F12 — P2 — `LOGIN_ALIASES` duplicated as hardcoded literals, no compile-time link
**File/lines:** `agent/lib/browser-pay.ts:12-15` (`LOGIN_ALIASES = { login: "site_login", password: "site_password" }`) vs `convex/lib/browserProfilePolicy.ts:22-29` (`loginVaultTask`: literal strings `` `site_login` ``/`` `site_password` `` in the prompt text, not imported from `LOGIN_ALIASES`).
**What happens:** today the strings match, so the Cloud agent correctly types into the aliases the server actually created via `loginBindings` (`agent/lib/browser-pay.ts:71-85`). But if either literal is ever changed independently, the vault-login run's prompt would ask the Cloud agent for an alias name that doesn't exist in `secretBindings`, silently breaking vault-based login typing with no compiler error and no failing check (the check in `scripts/browser-pay-check.ts:71-72` also hardcodes the literal strings rather than importing `LOGIN_ALIASES`).
**Why:** `browserProfilePolicy.ts` doesn't import from `browser-pay.ts` (likely to avoid a `convex/` → `agent/` dependency direction), so the string got duplicated by hand instead.
**Fix:** move `LOGIN_ALIASES`/`PAY_ALIASES` (or just the alias name strings) into a shared, dependency-free module (e.g. `convex/lib/`) that both `browserProfilePolicy.ts` and `browser-pay.ts` import.
**Check script:** update `scripts/browser-pay-check.ts` and `scripts/profile-sync-check.ts` to import and compare against the same constant instead of two independent literals.

## 3. Ideas

- **Persist paid-run state on the tenant row** (`browserPaying`, `browserPayHosts`) so every settle path can correctly gate `maybeRecordOrder`. Size M. Files: `convex/schema.ts`, `convex/tenants.ts` (`setBrowser`), `agent/tools/browser_task.ts`.
- **Give `profile_setup` a `nextBrowserAction`-equivalent reuse/poll guard.** Size M. Files: `agent/tools/profile_setup.ts`, possibly extract a shared helper from `agent/lib/browser-policy.ts`.
- **Add a "resume after out-of-band confirmation" inject kind** (готово/оплатил/сделано) that requeues into a session even after its run went terminal. Size M. Files: `convex/lib/browserInjectPolicy.ts`, `agent/tools/browser_task.ts`.
- **Fold `errandStartUrl` into the vault-login lookup** for keyword-only errands. Size S. Files: `agent/tools/browser_task.ts`.
- **Retire or scope `BROWSER_USE_PROFILE_ID`** to a single named owner tenant. Size S–M. Files: `agent/lib/browseruse.ts`, `agent/tools/profile_setup.ts`, `agent/tools/browser_task.ts`.
- **Hash the phone for Browser Use Cloud profiles** the same way `profileNameForTenant` does for Kernel. Size S. Files: `agent/lib/browseruse.ts` (new helper), call sites.
- **Scrub `run.result` for secret-shaped substrings inside `hydrate()`.** Size S. Files: `agent/lib/browseruse.ts`.
- **Bridge `job_open`/`job_wait` into the login/live-view detour** so the original errand is a durable record, not just context. Size M/L. Files: `agent/tools/profile_setup.ts`, `agent/tools/browser_task.ts`, `convex/jobs.ts`.
