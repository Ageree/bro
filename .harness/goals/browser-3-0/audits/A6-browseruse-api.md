Scope: `agent/lib/browseruse.ts`, `convex/lib/browseruse.ts`, `convex/lib/browserLivePolicy.ts`,
`convex/lib/browserCdp.ts`, `agent/lib/browser-pay.ts`, `agent/tools/browser_task.ts`,

the v4 REST API directly with `fetch` (confirmed by `find / -iname "*browser-use*"` returning
nothing under `node_modules`).

## 2. Findings (repo-side problems, prioritized)

**F1 — P1 — Cloud runs/browsers are never cancelled or stopped (cost leak + orphaned live sessions on give-up/reset).**
- Where: `agent/tools/browser_task.ts:576` (`reset` path builds a fresh run via `startRun(task, undefined, …)`, discarding `tenant.browserSessionId`/`browserRunId` with no cleanup call); `convex/lib/browserFollowPolicy.ts` give-up path (`nextFollowDecision` → `"giveup"`) also never cancels the abandoned run.
- What happens: human says "забудь, начни заново" or the 20-minute internal give-up fires → Bro starts (or the human triggers) a new session, but the old Browser Use Cloud run/browser keeps running and billing (`$0.02/h` + any live LLM turns) until Browser Use's own 4-hour hard cap kills it, or until an operator manually calls the vendor API. Doc-confirmed endpoints exist for exactly this (`POST /runs/{id}/cancel`, `PATCH /browsers/{id} {"action":"stop"}`), so this is a fixable gap, not a vendor limitation.
- Why: no code path in the repo ever hits `/runs/*/cancel` or `/browsers/*` (confirmed by repo-wide grep).
- Proposed fix: add a small `cancelRun(runId)` in `agent/lib/browseruse.ts` (`POST /runs/${runId}/cancel`) and call it from the `reset` branch of `browser_task.ts` before starting the new run, and from the Convex give-up wakeup handler in `convex/browserFollow.ts`. Fire-and-forget with `.catch(console.error)` in the same style as `followKick`.
- Check script: extend `scripts/browser-queue-check.ts` (or a new `browser-cancel-check.ts`) with a fetch-mock asserting `reset:true` issues a `POST /runs/{oldRunId}/cancel` before the new `POST /runs`.

**F2 — P2 — `isTerminal`/`DONE` status sets include undocumented values (`stopped`, `error`, `canceled`), while the only real terminal states are `completed`/`failed`/`cancelled`.**
- Where: `agent/lib/browseruse.ts:529-533` (`isTerminal`), `convex/lib/browserFollowPolicy.ts:1-8` (`DONE` set).
- What happens: harmless today (dead branches — the API will never actually emit `"stopped"`/`"error"`/`"canceled"`), but it signals the author wasn't fully sure of the real enum, and if the vendor ever adds a genuinely different value (e.g. some future `timed_out`), this code wouldn't need touching for the documented ones, but also wouldn't warn if reality permanently returns something in neither list — it would just silently loop-and-poll it as non-terminal until `pollGiveUp` fires at 20 min.
- Why: no direct root cause bug; just an unverified assumption.
- Proposed fix: no urgent change needed since it's a superset (safe); optionally tighten the comment to cite the confirmed 6-value enum and note the extras are speculative padding, and lower the risk from "assume terminal" to "explicit poll-give-up will still catch it" for the day the API returns something else.
- Check script: `scripts/browser-policy-check.ts` already exercises `isActiveStatus`/`isDoneStatus` — no change required, just documentation value.

## 3. Ideas (beyond bugs)

**I1 — Add `POST /runs/{id}/cancel` + `PATCH /browsers/{id} {"action":"stop"}` on reset/give-up/job_done.** (S, ties into F1)
Stops paying for an abandoned browser the moment the human resets or Bro gives up, instead of relying on the vendor's 4-hour hard cap. Files: `agent/lib/browseruse.ts` (new `cancelRun`), `agent/tools/browser_task.ts` (reset branch), `convex/browserFollow.ts` (giveup branch), `agent/tools/job_done.ts` if jobs also park a run.

**I2 — Fetch and send the final-state screenshot/recording as a Telegram/iMessage photo when a run completes.** (M)
Vendor doc trail: `GET /browsers/{id}` (single-GET, not list) is documented to carry a `recordingUrl` presigned S3 link once the browser stops, and list-endpoint docs explicitly call out a `screenshot_url` presigned field that exists per-session but is omitted from list responses for perf reasons — meaning a single `GET /browsers/{id}` (or equivalent single-session GET) likely exposes it. Today `settle()`/`payload()` in `agent/tools/browser_task.ts:89-104` only ever sends text. A photo of the final page (order confirmation, taxi ETA screen) would make "Bro writes first" much more convincing than a text summary. Needs one more direct doc/API probe to nail the exact field name before building (see Open questions).

**I3 — Use the documented session-share endpoint (`POST/PATCH /sessions/{id}/share`) instead of raw `liveUrl` for links sent to the human.** (S)
`create-session-share.md` describes a stable, re-activatable share token ("a link that was toggled off keeps working when re-enabled"). Bro currently texts the raw `liveUrl` scraped from run events (`convex/lib/browserLivePolicy.ts`), which per the docs is not guaranteed stable/long-lived. Switching OTP/live-view links to the share endpoint could fix "the live-view link died because the run object rotated" type bugs, if that's one of the "holes in доводка" the owner mentioned. Files: `agent/lib/browseruse.ts` (new `getOrCreateShare`), `agent/tools/profile_setup.ts`, `convex/lib/browserLivePolicy.ts` consumers.

**I4 — There is no webhook in v4 (confirmed absent) — do not spend time looking for one; instead shorten/adapt the poll cadence.** (S)
Since `run.completed` webhooks don't exist, the only lever available is `POLL_INTERVAL_MS` (2 min) and `FOLLOW_FIRST_SLEEP_MS` (20 s) in `convex/lib/browserFollowPolicy.ts:10-12`. If «доводка» latency is a real pain point, the fix is a tighter poll schedule (e.g. exponential 5s→10s→20s→60s→120s) rather than a webhook migration, since the vendor gives none.
